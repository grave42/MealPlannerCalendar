# Task for Develop

## Overview

Задача на разработку — это **самодостаточный файл**, который читает человек и которым можно передать работу другому агенту. Исполнитель понимает **зачем**, **что** и **когда готово**, не видя этого чата и не задавая вопросов.

## Процесс создания

1. **Собрать данные.** Из запроса пользователя и кода проекта (прочитать затронутые файлы, `git log`, структуру). Недостающее по обязательным разделам — спросить пользователя, по одному вопросу за раз. Не выдумывать.
2. **Заполнить шаблон** (ниже), все 12 разделов (раздел «Дизайн» — по условию, см. ниже).
3. **Сохранить файл** `docs/tasks/<YYYY-MM-DD>-<slug>.md` (slug — латиницей через дефис). Создать каталог, если его нет. Код самой задачи не писать.
4. **Показать пользователю** путь и краткое резюме (название, цель, оценка); попросить подтвердить или поправить.
5. **Сообщить, как передать:** «Реализуй задачу из `docs/tasks/<файл>`».

Никаких «как обсуждали выше»: только явные факты, пути и команды.

## Обязательные разделы

Выводить строго в этом порядке:

| # | Раздел | Что содержит | Критерий заполненности |
|---|--------|--------------|------------------------|
| 1 | **Название** | Глагол + объект, до 80 символов | Понятно без чтения тела |
| 2 | **Контекст / Проблема** | Почему задача появилась, кому и что мешает | Есть пользователь/система и боль |
| 3 | **Цель** | Желаемый результат в 1–2 предложениях | Измеримо или проверяемо |
| 4 | **Scope (входит / не входит)** | Два списка границ | Есть хотя бы 1 пункт «не входит» |
| 5 | **Требования** | Нумерованный список функциональных/нефункциональных требований | Каждое проверяемо |
| 6 | **Критерии приёмки** | Given/When/Then или чек-лист | Минимум 1 позитивный и 1 негативный сценарий |
| 7 | **Дизайн** | Макеты, экраны, состояния, тексты, поведение UI (см. «Раздел Дизайн») | Заполнен, если в задаче есть пользовательский интерфейс; иначе «Нет — UI не затрагивается» |
| 8 | **Технические детали** | Затронутые модули, API, данные, ссылки | Указаны файлы/сервисы или «неизвестно — нужен анализ» |
| 9 | **Зависимости и риски** | Блокеры, связанные задачи, что может пойти не так | Явно «Нет», если пусто |
| 10 | **Тестирование** | Какие тесты нужны (unit/integration/manual) | Привязано к критериям приёмки |
| 11 | **Оценка и приоритет** | Размер (S/M/L или часы) и приоритет | Оба значения указаны |
| 12 | **Инструкции для агента-исполнителя** | Ветка, команды сборки/тестов, ограничения, порядок работы, определение «готово» | Есть команды проверки и явные запреты |

## Раздел «Дизайн»

Условие: если для решения задачи нужен пользовательский интерфейс (новый экран, форма, кнопка, изменение существующего UI) — раздел заполняется обязательно. Если UI не затрагивается (чистый backend, миграции, API) — написать «Нет — UI не затрагивается» и не выдумывать содержимое. Если UI нужен, но макетов нет — спросить пользователя.

Содержимое (только применимое):
- **Макеты/референсы:** ссылки (Figma и т.п.) или путь к файлам в репозитории; описание словами, если макета нет.
- **Экраны и элементы:** список экранов/компонентов, расположение, ключевые элементы (поля, кнопки, таблицы).
- **Состояния:** загрузка, пусто, ошибка, успех, disabled; валидация полей.
- **Поведение и сценарии:** действия пользователя → реакция интерфейса, навигация.
- **Тексты:** подписи, плейсхолдеры, сообщения об ошибках (на русском).
- **Дизайн-система:** используемые компоненты, цвета, отступы, адаптивность, доступность (a11y).
- **Связь с API:** какие эндпоинты и поля использует экран.

Критерии приёмки и «Тестирование» должны включать проверяемые UI-сценарии (в т.ч. ошибка и пустые данные); в «Инструкциях для агента» — команды запуска/проверки UI и запрет отступать от макета без согласования.

## Соответствие правилам проекта (APPEND_SYSTEM.md)

Задачи пишутся для проектов по правилам из `~/.pi/agent/APPEND_SYSTEM.md` (стек: Java 21, Spring Boot 3.5 WebFlux + R2DBC, Liquibase, Lombok, MapStruct). Перед заполнением сверься с ними; не предлагай подходов, которых там нет, без явной просьбы пользователя. Если проект явно другой (не Java/Spring) — укажи это в «Технических деталях» и не навязывай эти правила.

**Технические детали** раскладывай по слоям (`controller` → `service` → `dao/repository` → `dao/model/entity|json|type` → `mapper` → `model/request|response` → `exception` → `utils/validator` → `config`) с путями файлов в корневом пакете `com.<org>.<app>`. Указывай:
- эндпоинты вида `/api/v1/<ресурс-в-единственном-числе>`, возвращаемые типы `Mono`/`Flux`; entity наружу не отдаются, нужны отдельные Request/Response DTO с `@Schema`;
- изменения БД — новый Liquibase changeSet `db/changelog/init/changelog-<N.M>-create_table-<table>.xml` (или `initData`), с `<comment>`, `remarks`, `<rollback>`, подключение в `changelog-master.xml`; применённые changeSet не править;
- новые enum/JSONB-поля — пара converters и регистрация в `DatabaseConfig.r2dbcCustomConversions`;
- ошибки — через иерархию `<App>Exception` (`NotFoundException`, `BadRequestException`, `ValidationException`, `ImpossibleOperationException`) с `userMessage` на русском; HTTP-маппинг только в `GlobalExceptionHandler`;
- новые свойства — `@ConfigurationProperties` под префиксом `app`; новые зависимости — в сгруппированный блок `build.gradle`.

**Требования** (нефункциональные) включают, где применимо: неблокирующая реактивная цепочка (без `block()`/`Thread.sleep`), запись под `@Transactional`, контекст через Reactor Context (без `ThreadLocal`), комментарии/Javadoc/логи/пользовательские сообщения на русском.

**Тестирование** — по конвенциям проекта: `src/test/java/<зеркальный пакет>/XxxTest.java`, `@DisplayName("Класс Xxx")`, `@Nested` со сценариями на русском; контроллеры — `@WebFluxTest` + `WebTestClient` + `@MockitoBean`; сервисы — `@SpringJUnitConfig` + `StepVerifier`. Для каждого эндпоинта/бизнес-логики — минимум успешный и ошибочный сценарий, сопоставленный с критериями приёмки.

**Инструкции для агента** обязательно включают: команды `./gradlew build` и `./gradlew test`; запреты (field injection, `block()`, импорты `*`, мёртвый закомментированный код, правка применённых changeSet, коммит секретов); код-стайл (4 пробела, K&R, Lombok `@RequiredArgsConstructor`, `@Slf4j` с параметризованными логами на русском); коммиты — короткие английские в стиле `Add …` / `Fix …`.

## Пример заполнения

```markdown
---
title: Добавить экспорт списка заказов в CSV
status: ready
priority: High
estimate: M
created: 2025-01-15
---

# Добавить экспорт списка заказов в CSV

## Контекст / Проблема
Менеджеры по продажам вручную копируют таблицу заказов в Excel для
еженедельного отчёта (~30 мин в неделю на человека), возникают ошибки копирования.

## Цель
Менеджер выгружает отфильтрованный список заказов в CSV одной кнопкой.

## Scope
**Входит:**
- Кнопка «Экспорт CSV» на странице «Заказы»
- Экспорт с учётом текущих фильтров
**Не входит:**
- Экспорт в XLSX/PDF
- Автоматическая рассылка отчётов

## Требования
1. Эндпоинт `GET /api/orders/export?format=csv` принимает те же фильтры, что и список.
2. Колонки: id, дата, клиент, сумма, статус. UTF-8 с BOM, разделитель `;`.
3. Экспорт до 50 000 строк; потоковая отдача без загрузки всего набора в память.
4. Доступно только ролям `manager` и `admin`.

## Критерии приёмки
- Given менеджер с фильтром «статус = оплачен», When нажимает «Экспорт CSV»,
  Then скачивается файл только с оплаченными заказами.
- Given пользователь с ролью `viewer`, When вызывает эндпоинт, Then 403.
- Given выборка > 50 000 строк, When экспорт, Then 422 с понятным сообщением.

## Дизайн
- Макет: ссылка на Figma (страница «Заказы»); кнопка «Экспорт CSV» справа в тулбаре рядом с фильтрами.
- Состояния: при выгрузке кнопка disabled со спиннером; при 422 — toast «Слишком много строк (макс. 50 000), уточните фильтры».
- Тексты: подпись «Экспорт CSV», имя файла `orders-<YYYY-MM-DD>.csv`.

## Технические детали
- Backend: `orders/controller.ts`, `orders/service.ts`
- Frontend: `pages/Orders/Toolbar.tsx`

## Зависимости и риски
- Зависит от ORD-112 (единые фильтры). Риск: нагрузка на БД при больших выгрузках.

## Тестирование
- Unit: форматирование CSV (кавычки, `;` в значениях)
- Integration: фильтры + права доступа
- Manual: открытие файла в Excel, кириллица читается

## Оценка и приоритет
M (≈2 дня), приоритет: High

## Инструкции для агента-исполнителя
- Работай в ветке `feature/orders-csv-export`; схему БД не менять.
- Новых зависимостей не добавлять; для CSV использовать уже подключённый `csv-stringify`.
- Порядок: unit-тесты форматирования → сервис → контроллер → кнопка на фронте.
- Проверка: `npm test` и `npm run lint` проходят.
- Готово, когда выполнены все критерии приёмки и обновлён `docs/api.md`.
- Если требование неясно или противоречит коду — остановись и задай вопрос, не додумывай.
```

## Пример плохого заполнения

| Плохо | Почему | Исправление |
|-------|--------|-------------|
| Название: «Сделать экспорт» | Непонятно что и куда | «Добавить экспорт заказов в CSV» |
| Цель: «Улучшить отчёты» | Не проверяемо | «Выгрузка в CSV одной кнопкой» |
| Критерий: «Работает быстро» | Нет метрики | «50 000 строк < 10 с» |
| Scope без «Не входит» | Скрытое расширение задачи | Явно перечислить исключения |
| «Делай как в чате» | Агент не видит чат | Выписать факты в файл |

## Правила работы

- Раздел неизвестен → спросить пользователя; не писать «TBD» молча.
- Раздел не применим → «Нет» с причиной, но раздел не удалять.
- Каждый критерий приёмки покрыт в разделе «Тестирование».
- Файл пишется на языке пользователя; пути, команды и идентификаторы — как в коде.
- Секретов, токенов и паролей в файле быть не должно.

## Частые ошибки

- Решение вместо проблемы в «Контексте» (описано *как*, не *зачем*).
- Критерии приёмки дублируют требования без проверяемых сценариев.
- Нет негативных сценариев и границ (права, лимиты, пустые данные).
- Ссылки на контекст чата вместо явных фактов.
- Нет команд проверки в инструкциях для агента.
- UI нужен, а раздел «Дизайн» пуст или без состояний (ошибка, пусто, загрузка); либо для backend-задачи выдуман дизайн.
- Задача противоречит правилам из `APPEND_SYSTEM.md` (блокирующий вызов, отдача entity наружу, правка применённого changeSet, ORM-генерация схемы).
